# grid_stride_known.txt -- the kernels whose Slang port makes NO covering loop over
# work the CUDA covers with a grid-stride loop.  Read by tools/check_grid_stride.py.
#
# THIS IS A RATCHET, not a permission slip.  A NEW omission fails the check, and so
# does an entry left here after its port was fixed -- a stale allowlist is how a
# ratchet quietly stops ratcheting.  The list may shrink; it may not grow.
#
# WHAT AN ENTRY COSTS.  Past its ceiling the port does not degrade gracefully.  On
# the sphere-vs-heightfield core the uncovered pairs left their records unwritten and
# convexTrimeshCorrelate dereferenced the uninitialised contact count (P9.52b-6,
# SIGSEGV).  On the convex heightfield core a half-3 box fell straight through the
# terrain (P9.58, final y = -70.8).
#
# ---------------------------------------------------------------------------
# THE FIRST VERSION OF THIS FILE LISTED 38 KERNELS AND 26 OF THEM WERE NOT DEFECTS
# ---------------------------------------------------------------------------
# P9.59 looked for `WorkgroupCount()` in the entry body and called everything else a
# one-pass port.  That marker was wrong for this corpus.
# `PxgVulkanCudaContext::launchKernel` takes `unsigned int /*blockDimX*/,
# /*blockDimY*/, /*blockDimZ*/` -- names commented out -- and forwards only gridDim to
# vkCmdDispatch, so THE CUDA blockDim HAS NO RUNTIME SPELLING HERE.  A shader
# reproducing `i += gridDim.x * blockDim.y` cannot write it as an expression; the
# corpus idiom is a file-scope `static const` holding the product for the one launch
# site.  Several of those shaders warn in their own headers that deriving the stride
# from the group count instead would double-visit or skip.
#
# The 26 were ports that loop, written the way this port has always written them.
# P9.60b widened the check to accept a named stride, and to follow one level of
# same-file helper calls (several entries are two-line wrappers around the loop).
#
# ---------------------------------------------------------------------------
# WHAT THE CHECK STILL CANNOT DO
# ---------------------------------------------------------------------------
# It finds MISSING loops, not WRONG ones.  A port looping with an incorrect constant
# passes, because deciding correctness needs the launch site and that is C++ the
# checker does not parse.  One concrete case is open:
# `writeoutAccumulatedForcePerObject` loops with a named stride, so the checker clears
# it, while P9.60's reading classified it a real omission.  That disagreement is
# unresolved and belongs to a human, not to this file.
#
# ---------------------------------------------------------------------------
# The 12 below are what the widened check reports AND what P9.58's independent
# adversarial audit confirmed at the source -- two methods that started from
# different evidence and converged.  They are real; they are unfixed.
#
# P9.61 removed the five skinning entries.  Two of them (zeroNormals,
# normalizeNormals) were not a ceiling problem at all: the engine launches them
# with a block of 1024 while the shader declares 256, and the bridge drops
# blockDim, so they reached a QUARTER of the guide vertices on EVERY call.  The
# fixture could not see it because it sized its own grid to the shader (ceil(n/256))
# and used meshes of 20-50 vertices, below one group either way.  Given the engine
# divisor and meshes above 256, it failed with 1820 mismatches before the fix.
#
# ---------------------------------------------------------------------------
# P9.63 -- A THIRD FALSE-POSITIVE SHAPE, AND THE LAST TWO REAL ONES
# ---------------------------------------------------------------------------
# Reading the four unmeasured entries at their LAUNCH SITES split them cleanly.
#
#   ps_primitivesCollisionLaunch          NOT omissions.  psContactGenBda.slang
#   ps_primitivesDiffuseCollisionLaunch   hoists the trip count and steps by one:
#       const uint stride = PS_BLOCK * PS_GRID;
#       const uint nbIterations = (totalComparison + stride - 1u) / stride;
#       for (uint it = 0u; it < nbIterations; ++it)
#           const uint workIndex = it * stride + gid.x * PS_BLOCK + tid;
#   That is a grid-stride loop with the multiply moved out of the increment and
#   into the index -- every work item visited exactly once -- but `++it` matches
#   neither of the checker's two markers.  check_grid_stride.py now accepts a
#   counted loop whose variable scales a named product; both entries are gone.
#
#   updateBodiesLaunchDirectAPI           REAL, and now fixed.  Both were literally
#   updateBodyExternalVelocitiesLaunch    `const uint i = dispatchThreadId.x;
#                                         if (i >= gParams.count) return;`
#   against a CUDA that loops.  Engine launch for both: grid 64, block 256, so the
#   ceiling was 16384 records.  Past it the external-velocity kernel DROPPED user
#   setLinearVelocity/addForce calls, and the direct-API kernel left new bodies
#   holding an uninitialised PxgBodySim on their first transfer.  Neither fails
#   loudly -- which is why neither had an observing scene and both survived to the
#   end of the list.  Fixed in bodyUpdate.slang; both left PXG_HLSL_ENTRIES because
#   the stride needs WorkgroupCount().
#
# ---------------------------------------------------------------------------
# The two below are the whole remaining list.  Both are 8x SHORT ON EVERY CALL,
# not merely capped: the engine launches them with blockDim 256 and numBlocks 512
# while the shader declares [numthreads(32,1,1)], and the bridge drops blockDim, so
# they reach an eighth of the cloth vertices whatever the scene size.  They are
# NOT fixed here because both manifest rows are annotated "emits no contacts
# upstream" and gated by check_disabled_kernels.py -- the contact gen they feed is
# itself dead, so a fix would be unobservable and untestable today.  When that
# upstream is revived the loop is the FIRST thing to add, and this note is the
# record that it is missing.
cloth_heightfieldVertexContactGenLaunch
cloth_meshVertexContactGenLaunch
