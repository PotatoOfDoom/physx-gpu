# P9.83b-4: the MEASURED budget for doTriangleTriangleCollision
# (convexMeshMidphase.cu:972-1231), taken from a probe that computes nothing --
# npTriTriSharedProbe.slang -- because the answer decides whether that kernel can
# be ONE entry point at all, and it was needed before the kernel was written.
#
# P9.83b-pre PROJECTED 34816 and called the kernel blocked.  P9.83b-2 argued the
# blocker dissolves once the reduction is serial, because the warp-emulated
# form's gPxgWarpScratch (4096 B) goes away: 34816 - 4096 = 30720.  The probe
# declares the CUDA's nine shared buffers one for one and omits gPxgWarpScratch,
# and the answer is 30168 -- so the argument was right, and it is now a
# measurement instead of an argument.  The kernel FITS.
#
# THE FIRST NUMBER HERE WAS 30168, AND IT WAS A PARTIAL MEASUREMENT.  It counted
# the nine buffers doTriangleTriangleCollision declares itself and missed two that
# the helpers it calls SELF-ALLOCATE: `offset` in findInterestingTrianglesA
# (sdfCollision.cuh:624) and `perWarpCountS[32]` in the two-argument
# threadBlockScanExclusive<32> (reduction.cuh:628), which is the overload
# addIndexToBuffer actually calls.  +132 bytes.  A probe that measures nine of
# eleven buffers reads exactly like one that measures eleven, which is the whole
# reason this ratchet stores a number instead of a verdict -- it is what caught
# the growth.
#
# IT FITS BY 2468 BYTES, which is 92.5% of the limit.  That is the entire point of
# the entry: one module import carrying Workgroup storage, one more field on
# SparseSdfTexture, or MAX_MESH_MESH_PATCHES moving off 128, and the pipeline stops
# being creatable.  16384 of the 30300 is patchesS[128] alone.
#
# A CONCRETE NEAR MISS, already found: pxgSlangSdfFind.slang holds the Slang port
# of findInterestingTriangles/addIndexToBuffer and declares its OWN module-level
# Workgroup buffers -- gSdfIndices[1024] (4096 B), gSdfIndices2[1024] (8192 B),
# gSdfPerWarpCount[32], gSdfOffset, gSdfGlobalOffset, ~12424 B in total.  Reusing
# it is the obvious move and is affordable ONLY if the entry point never touches
# the uint-variant gSdfIndices, since gSdfIndices2 replaces this kernel's own
# triangleIndicesS rather than adding to it.  Touch both and the budget is 34396
# and the pipeline cannot be created.  That is a measurement to take, not to
# reason about, when the kernel is wired.
#
# THIS ENTRY IS TEMPORARY.  When the real kernel lands it supersedes the probe,
# and the probe -- along with this entry and its pxg_compile_shader line -- is to
# be DELETED, not left behind measuring a budget nothing spends.
# P9.83b-4 (3/n): THE WARP-STAGING QUESTION, AND A CORRECTION TO P9.83b-2.
# That tranche argued the 34816-byte blocker dissolves once the contact reduction
# is serial.  It covers ONE of the THREE contactReduce2 call sites -- :472, inside
# reduceContactsSingleWarp under `if (warpIndex == 0)`.  The other two, :810 and
# :931, are block-uniform and called by ALL 32 WARPS, each on its own 32 lanes,
# and a serial per-warp reduce needs those lanes somewhere addressable.  Measured:
#
#   all 32 warps staged at once (32*32*16 B)   46684 bytes -- OVER BY 13916
#   one warp at a time         (32*16 B)       30812 bytes -- fits, 1956 spare
#
# So the design is forced, not chosen: 32 sequential per-warp reduces per call
# site.  The wide entry point was deleted after it was measured -- an entry point
# over the limit by construction fails this checker for the whole corpus, and a
# number belongs in this file, not in a shader nobody can compile.
npTriTriSharedProbe:triTriSharedProbe    30300
npTriTriSharedProbe:triTriSharedProbeNarrowStage    30812
